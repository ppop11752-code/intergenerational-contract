# UI PRODUCTION VISUAL FIDELITY AUDIT — v1.0.0

**Date:** 2026-09-08  
**Owner:** 05 — UI/UX & ART  
**Trigger:** `H-20260908-092-05-PRODUCTION-VISUAL-FIDELITY-AUDIT`  
**Published baseline:** tag `v1.0.0`  
**Audit result:** **FAIL — MAJOR PRODUCTION VISUAL FIDELITY MISMATCH**

## 1. Executive conclusion

Published v1.0.0 is functionally much closer to the approved UX semantics than its appearance suggests, but the **visual production layer is not a faithful realization of the user-approved design**.

This is not a request for a new art direction. The authoritative design direction remains the already-approved one:
- pixel art + Japanese anime/chibi Characters;
- bright/lively fantasy settlement as the primary world;
- parchment/wood/dark-fantasy pixel chrome;
- screen-specific compositions approved in the V1 specs;
- three-role typography rather than mono everywhere;
- asset-driven production visuals rather than CSS/dev-placeholder geometry.

The user's post-release feedback that v1.0.0 looks visually poor is consistent with the published implementation and is treated as a new authoritative signal that prior structural/asset QA did **not** establish visual fidelity.

No gameplay, protocol, authoritative timer, economic rule or state semantic is changed by this audit.

## 3. Root-cause findings

### RC-01 — Generated placeholder-quality raster art was promoted to production
**Severity:** MAJOR VISUAL MISMATCH

The locked art contract requires anime/chibi portraits, an asset-driven fantasy world, civic-fantasy Government, differentiated Residence architecture, parchment/wood/dark-fantasy frames and production icons.

Actual v1 art is generated by `.github/scripts/generate_ui_art_v1.py` using basic Pillow primitives (`rectangle`, `polygon`, `ellipse`, flat fills and lines). Examples:
- portraits are assembled from rectangular skin/hair/body blocks and a few eye/mouth pixels;
- Government and Residences are generated from a generic `building()` primitive;
- terrain/path/vegetation tiles are procedural geometric shapes;
- frames/buttons are rectangular primitive borders.

These binaries are technically valid raster assets, but **binary validity is not equivalent to production art quality**.

**Violates:**
- `docs/UI_USER_DESIGN_DECISIONS_2026-09-07.md` items 1, 3, 10–14, 21–23, 28–31;
- `docs/UI_ART_ASSET_CONTRACT_V1.md` sections 1, 4–10, 13, 15–17;
- `docs/UI_LANDING_APPROVED_V1.md`;
- `docs/UI_ROOM_APPROVED_V1.md`.

### RC-02 — The final UI is a stack of semantic patches over a generic base rather than one coherent visual system
**Severity:** MAJOR VISUAL MISMATCH / IMPLEMENTATION ARCHITECTURE

`index.html` loads the base UI plus multiple presentation/follow-up/finalization layers. Several approved surfaces are produced by decorating/repositioning earlier generic feature sheets rather than rebuilding their intended composition.

Result:
- semantics frequently match the approved rules;
- composition and hierarchy are only approximated;
- generic CSS panels and development geometry remain visually dominant;
- later overrides accumulate inconsistencies in spacing, density and scale.

This is an implementation-fidelity problem, not a gameplay problem.

### RC-03 — Visual QA verified asset presence and DOM/runtime conditions, not fidelity
**Severity:** MAJOR PROCESS GAP

`qa/uiux-art-final-e2e.mjs` verifies items such as:
- required asset requests return successfully;
- raster assets are attached to Government/Residence/terrain;
- icons render at 24 px;
- frames are active;
- ambience is non-blocking;
- raw IDs are hidden;
- timers continue while UI/art is open.

It also saves `desktop.png` and `mobile.png`, but there is **no approved-reference screenshot comparison, image diff, layout tolerance check or human visual-signoff assertion** in the test.

Therefore a prior QA PASS proves runtime/structural integration, not that the released UI looks like the approved design.

### RC-04 — Prior binary review over-claimed visual adequacy
**Severity:** MODERATE PROCESS GAP

`docs/UI_ART_BINARY_REVIEW_V1.md` approved the generated portrait/world/chrome batches as compatible with the direction. The current production audit, supported by direct user feedback and actual released raster inspection, overturns any interpretation that this approval established final visual fidelity.

The binary package may remain useful as a development fallback, but it must no longer be treated as final production art.

## 5. What is NOT a visual-design defect

The following are intentionally separated from this audit:

### Gameplay / authoritative semantics
No gameplay redesign is requested. Approved rules/timers/actions remain authoritative.

### Functional QA
A surface being clickable, synchronized, responsive, server-authoritative or regression-tested is valuable, but is not evidence of visual fidelity.

### Personal taste / new redesign requests
This audit does not ask for a different theme, new layout direction or new visual concept. Corrections must return to the **existing user-approved V1 sources**. Any new art direction requires a new user decision and is outside H092.

### Potential implementation bugs
If a control/state is functionally missing, stale or server-inconsistent, route that issue to Chat 06/03/07 under the appropriate implementation/QA process. This audit only records visual drift unless the visual defect is caused by the implementation architecture itself.

Treat the current generated `ui/v1` raster pack as **development fallback / placeholder-quality**, not final fidelity evidence.

#### P0.2 Rebuild Landing visual composition around approved assets
Preserve approved left-menu/right-key-art layout, but replace the current primitive CSS composite with a production composition matching `UI_LANDING_APPROVED_V1.md`.

Acceptance:

- exactly three readable anime/chibi foreground Characters;

Preserve all current authoritative map interactions.

Replace pervasive mono/default heading usage with visually distinct roles:

## 7. Implementation architecture correction

For visual-correction work, Chat 06 should prefer **consolidation over another patch layer**:

1. identify the final component/style owner for each approved surface;
2. retire obsolete CSS/DOM decorators for that surface where feasible;
3. keep gameplay event bindings/state selectors unchanged;
4. create one authoritative production visual class/component path per surface;
5. keep temporary fallback assets explicitly marked as fallback, never silently accepted as final;
6. do not fix major composition mismatches solely by adding more late CSS overrides.

DOM presence, asset HTTP success, raster dimensions and `image-rendering: pixelated` are necessary but insufficient.
